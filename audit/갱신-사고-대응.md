# 갱신 사고 대응 절차 (한 장)
데일리 수집·배포가 멈췄거나 낡은 값이 나갈 때 **누가 · 몇 시간 안에 · 무엇을** 하는지 정한다(#102). 근거는 `.github/workflows/`의 `daily-update.yml`·`deploy.yml`·`summarize.yml`·`schedule-watchdog.yml`과 #97·#294·#506·#533이다. 시한은 제안이고 확정은 `TBD(owner)`다(끝 절).

## 먼저 알 것

- **구조(B, #510 컷오버):** main 은 **데이터만** 든다. `Daily update`·`Summarize`는 `docs/data`·`raw`만 커밋하고(`push-docs.sh`), 사이트는 `Deploy site`(`deploy.yml`)가 main HEAD 로 빌드·시험·게시한다. Daily 가 초록이어도 배포는 빨강일 수 있고 그 반대도 된다.
- **늦음은 전제다. 알림은 시각이 아니라 마지막 성공으로부터의 경과로 한다**(#294 data-analyst 규칙, [댓글](https://github.com/kyhsa93/jipgye/issues/294#issuecomment-6398315918)). 정기 run 은 `7 23 * * *`(08:07 KST) 하나뿐이고(#506) 예정보다 늦게 뜬다 - 23:07 칸 지연 중앙 2.7h·최대 4.4h(n=31), 전 틱 118건 중앙 5.4h·p90 7.3h·최대 9.5h, 누락 0건(09-24~10-24).
- **경과 단계:** 마지막 성공 뒤 **30h 미만 = 지연, 조치 없음 · 30~54h = 확인만(실패 run 이 있는지) · 54h 초과 = 알림**(워치독 `Schedule watchdog`, #322·#499·#533: 36h 안 schedule run 0건 / 54h 안 Daily 성공 0건 / 54h 안 Deploy site 성공 0건). 연속 23:07 run 간격은 22.3~25.2h라 **단발 실패(약 48~51h)는 알림이 아니고 빨간 run 이 맡는다. 연속 실패·누락은 알림이다.** 여유는 3.4h뿐이다. 일정(cron)은 지금 고치지 않는다(두 번째 cron 없음, 지연 수용).
- **초록 ≠ 갱신:** 수동 `mode=news` 는 `시장 지표 수집`·`실거래 수집`이 skipped 인데도 success 다(#97에서 이것이 full 실패를 가렸다). 목록의 한 줄이 아니라 **단계 결론**을 본다. 국토부 응답은 날짜별로 다시 받을 수 없다(#62).

## 시한과 담당

| 단계 | 담당 | 시한(제안) | 끝났다는 증거 |
|---|---|---|---|
| 감지·이슈화 | qa(점검 사이클), 워치독 | 실패 run 을 본 날 안(한도 24h) | `[오류]` 이슈 `audit`·`bug`, 마지막 정상·첫 실패 run id |
| 분류 | qa 재현, engineer 확정 | 이슈 뒤 같은 날, 갈래는 30분 안 | 갈래 하나, 실패 단계·영향 파일 |
| 복구 | engineer 구현, cto 승인·머지 | 코드 오류는 영업일 기준 다음 사이클 안 | 병합 PR, 롤백이면 revert 1건 |
| 소유자 보고 | coo 요약, pm 우선순위 | 아래 트리거 해당 시 같은 날 | 이슈 번호·마지막 정상·복구 시각·갈래·재발 방지 PR·소유자가 할 일 |
| 확인 | engineer, cto | 복구 직후 | 아래 넷 모두 |
| 기록·재발 방지 | engineer, coo 요약 | 복구 PR 에 포함 | 원인 줄 수정 + 큰 입력 재현 시험(#100), 같은 패턴 grep, 이슈 댓글 한 줄 |

복구 확인 넷: ① Daily 단계 결론 success ② main 에 `chore: 데일리 데이터 갱신 <날짜>` 커밋 ③ 이어진 `Deploy site` success ④ 배포본 JSON `updatedAt` 갱신(`node scripts/source-age.ts`가 이상 없음). 하나라도 빠지면 닫지 않는다. 감지 한도 24h 와 소유자 보고 한도(첫 실패부터 복구까지 24h)는 **같은 시계**(첫 실패 시각)다.

## 증상표

| 증상 | 먼저 볼 것 | 갈래 → 조치 |
|---|---|---|
| Daily red | 실패 단계: 뉴스 수집 → 시장 지표 수집 → 실거래 수집 → 기사에 실거래가 수치 붙이기 → 변경사항 커밋 및 푸시 | 코드 오류(스택·RangeError, 규모 의존이면 큰 입력 재현) → 수정 PR. 외부 소스(무응답·형식·키 만료) → 그 소스만인지 가르고 키는 소유자. 푸시 단계는 원격에 새 데이터 커밋이 있으면 일부러 실패(#92·#94) → 다음 틱이 최신 위에서 다시 만든다 |
| Deploy red | `사이트 생성`·`테스트 (build/site 기준)` 중 어디 | 사이트는 직전 배포에 머문다. 원인이 방금 병합이면 revert 1건 PR, 데이터면 수정 PR. `데이터 건강 점검 실패 반영`만 빨강이면 배포는 나갔다(비차단) |
| Test red on main | `test.yml --branch main` | 기능 시험이라 Deploy 와 별개. 원인 병합 커밋을 찾아 수정 1건 또는 revert 1건(cto). 시험 하한(COUNT)은 내리지 않는다 |
| 데이터 공백 | `git log --grep "데일리 데이터 갱신"`, `raw/` 슬롯 | 빠진 날은 메우지 않고 이슈에 날짜·범위를 적는다. 실거래 원본은 백필이 하루 상한만큼 메운다(README) |
| 낡은 금리·시계열 | `node scripts/source-age.ts`(상태줄 ≥2일, 이슈 댓글 ≥3일, #72) | `시장 지표 수집`의 소스·`ECOS_API_KEY`. 기준일 표시는 그대로 두고 가리지 않는다 |
| 늦은 틱 | `gh run list --workflow daily-update.yml --event schedule` | 마지막 성공 30h 미만이면 정상. 수동 실행 금지(#294). 30~54h 는 확인, 54h 초과·36h 무발화는 워치독이 울고 이슈로 올린다 |

## 명령 (읽기 전용)

```
gh run list -R kyhsa93/jipgye --workflow daily-update.yml --limit 10   # EVENT 열: schedule / workflow_dispatch. deploy.yml = Deploy site
gh run view <id> -R kyhsa93/jipgye --json jobs --jq '.jobs[].steps[] | "\(.name) \(.conclusion)"'   # skipped = news 모드
gh run view <id> -R kyhsa93/jipgye --log-failed        # 실패 로그. 비밀값은 붙여 넣지 않는다
node scripts/source-age.ts                              # 경과일 큰 순 + 마지막 줄 요약
node scripts/check-schedule-runs.ts --check=success     # 워치독과 같은 검사(--check=deploy, 인자 없음=36h 무발화). GITHUB_TOKEN 필요, 종료 1 = 경보
```

## 하지 않는 것

- force-push·이력 다시 쓰기 금지. 되돌림은 `git revert` 새 커밋 1건(PR, cto 병합)이고 main 에 직접 푸시하지 않는다.
- 소유자 허락 없이 수동 실행·재실행하지 않는다. 소유자가 `! gh workflow run daily-update.yml -f mode=full` 처럼 직접 돌리고, 에이전트는 요청만 한다. Daily·Summarize 는 한 줄(`digest-pipeline`)이라 진행 중이면 겹쳐 돌리지 않는다. `Deploy site` dispatch 는 롤백 전용이다.
- `docs/data`·`raw` 를 손으로 고쳐 숫자를 맞추지 않는다(수집기·빌더를 고친다). `raw` 커밋은 되돌리지 않는다. 시크릿(`MOLIT_*`·`ECOS_API_KEY`)을 이슈·댓글·로그·커밋에 쓰지 않는다. 시험을 끄거나 COUNT 를 내려 초록을 만들지 않는다. 유료 API·새 로컬 cron·서버는 쓰지 않는다.

## 소유자 결정 트리거

- **돈:** 키 재발급·유료 전환. **신원:** 계정·로그인·저장소 설정·시크릿 값, 수동 실행 허락. **법:** 개인정보·이용허락에 걸림.
- 공개 숫자가 틀린 채 노출된 정황, 첫 실패부터 복구까지 24h 초과, `source-age` ≥3일, 같은 원인이 7일 안에 두 번째. 올리지 않는다: 늦은 틱, 다음 틱에 자연 복구된 일시 장애(이슈 댓글 한 줄).
- 일정 재검토(#294): 23:07 틱 누락이 30일 안 2회 이상, 또는 23:07 칸 지연 최대가 6h 초과(54h 창 위험)이면 보조 cron 을 R2 PR 로 판단한다.

## #97 따라 해 보기 (당시 cron 넷)

| 시각(UTC) | 사건 | 이 문서라면 |
|---|---|---|
| 10-08 02:39 | 마지막 정상 full(37718918573) | 마지막 정상 run id 기록 |
| 10-09 02:54 | full 첫 실패(37876774770, `build-cancellation` RangeError, raw/sale 133,348건) | 신호 = 빨간 Daily. 이슈화 한도 24h |
| 10-09 09:13 | #97 생성(첫 실패 +6h19m) | 한도 안. 갈래 = 코드 오류(규모 의존), 재현 로그가 본문에 있다 |
| 10-09 10:26·14:17 | news 실행 success(37917570770·37943105870) | 단계 결론 skipped 로 가려낸다. 지금은 schedule news 가 없어 수동 news 만 해당 |
| 10-09 17:22 | PR #98 뒤 full 37965823232 success | 첫 실패 +14h28m < 24h, 보고 기준 미해당. 확인 ①②④ 충족(커밋 9de951f, `cancellation.json` 10-09T17:24:51Z) |

- **결론:** 문서대로면 #97은 빨간 run 이 첫 신호라 같은 날 안에 이슈가 서고 24h 안에 복구된다(실제 6h19m·14h28m). **지금의 cron 1개 기준** 워치독 54h 는 마지막 성공(10-08 02:39Z) 뒤 10-10 08:39Z 이후에야 울릴 수 있어 복구(약 38h43m)가 먼저다. 당시 cron 넷에서는 news 성공이 창을 갱신해 아예 울리지 않았다 - 백스톱이고 #97을 잡은 장치가 아니다. `source-age`도 KST 10-10 00:00~02:24 사이에만 ≥2일이라 못 잡는다. 지금 구조라면 수정 뒤 수동 full 은 소유자 몫이다. 바로 못 돌리면 다음 자연 틱(23:07Z + 2~5h)까지 첫 실패 +22~25h(01:07~04:07Z - 02:54Z)라 24h 경계에서 소유자 보고 대상이 된다.
