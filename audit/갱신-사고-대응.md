# 갱신 사고 대응 절차 (한 장)
데일리 수집·배포가 멈췄거나 낡은 값이 나갈 때 **누가 · 몇 시간 안에 · 무엇을** 하는지 정한다(#102). 근거는 `.github/workflows/`의 `daily-update.yml`·`deploy.yml`·`summarize.yml`·`schedule-watchdog.yml`과 #97·#294·#506·#533·#822이다. 시한은 제안이고 확정은 `TBD(owner)`다(끝 절).

## 먼저 알 것

- **구조(B, #510 컷오버):** main 은 **데이터만** 든다. `Daily update`·`Summarize`는 `docs/data`·`raw`만 커밋하고(`push-docs.sh`), 사이트는 `Deploy site`(`deploy.yml`)가 main HEAD 로 빌드·시험·게시한다. Daily 가 초록이어도 배포는 빨강일 수 있고 그 반대도 된다.
- **늦음은 전제다. 알림은 시각이 아니라 마지막 성공으로부터의 경과로 한다**(#294 data-analyst 규칙, [댓글](https://github.com/kyhsa93/jipgye/issues/294#issuecomment-6398315918)). 정기 run 은 `7 23 * * *`(08:07 KST) 하나뿐이고(#506) 예정보다 늦게 뜬다 - 23:07 칸 지연 중앙 2.7h·최대 4.4h(n=31), 전 틱 118건 중앙 5.4h·p90 7.3h·최대 9.5h, 누락 0건(09-24~10-24).
- **경과 단계:** 마지막 성공 뒤 **30h 미만 = 지연, 조치 없음 · 30~54h = 확인만(실패 run 이 있는지) · 54h 초과 = 알림**(워치독 `Schedule watchdog`, #322·#499·#533: 36h 안 schedule run 0건 / 54h 안 Daily 성공 0건 / 54h 안 Deploy site 성공 0건). 연속 23:07 run 간격은 22.3~25.2h라 **단발 실패(약 48~51h)는 알림이 아니고 빨간 run 이 맡는다. 연속 실패·누락은 알림이다.** 여유는 3.4h뿐이다. 일정(cron)은 지금 고치지 않는다(두 번째 cron 없음, 지연 수용).
- **Deploy site 는 경과보다 횟수가 먼저다(#822):** 마지막 성공 뒤 **run 2회 연속 실패 = 경과와 무관하게 알림**(`--check=deploy`의 둘째 규칙). 10-30 사고에서 사이트가 49.1h 멈추는 동안 54h 창은 울지 않았다(아래 「10-30 Deploy 사고 재생」). 단발 실패는 여전히 알림이 아니다.
  - **「연속 2회」:** 달력 이틀도 같은 커밋 두 번도 아니다. push·workflow_run run 을 `created_at` 최근 것부터 보며 성공 전까지의 실패 수다. 시간 창이 없어 28분 간격 둘도 2회다. 취소·건너뜀·진행 중은 끊지도 더하지도 않고, dispatch 는 안 센다.
  - **재실행은 같은 회다.** 그 run 의 지금 결론을 쓴다: 성공하면 실패가 없어지고(11-03 run 41562029140), 다시 실패해도 한 회다. 재실행을 누른 것은 누가 보고 있다는 뜻이다.
  - **빨강 ≠ 정지:** run 결론만 본다. `데이터 건강 점검 실패 반영`만 빨간 run 도 실패로 세므로, 울면 실패 단계부터 본다(증상표).
- **알림의 끝은 둘이다.** 실패 판정은 빨간 워치독 run 과 GitHub 실패 메일이다. 소유자가 메일 수신을 확인했다(2026-11-03). `::warning::` 만 내는 데이터 진척 경고는 run 이 초록이고 메일도 없어, 소스 묶음 8개는 `report` job 이 **이슈**로 올린다(아래 「데이터 진척 경고의 출구」). 그 밖의 경고(`news` 36h, `ledger` 기한, 빌더 산출물 30h)는 로그에 머물고 실패 단계에서 메일이 된다.
- **빌더 산출물 나이(F2, #657):** `docs/data/*.json` 최상위 `updatedAt` 이 30h 를 넘으면 로그, 54h 를 넘거나 없거나 못 읽으면 실패다(제외 5개는 `check-data-progress.ts` 의 `UPDATED_AT_EXCLUDED`). 빌더가 안 돌거나 소프트 실패해 어제 파일을 둔 경우만 잡는다. `updatedAt` 은 계산한 날이라 입력이 멈춘 채 다시 계산하면 못 잡는다. 수집이 전면 정지하면 F2 와 `--check=success` 가 함께 운다.
- **초록 ≠ 갱신:** 수동 `mode=news` 는 `시장 지표 수집`·`실거래 수집`이 skipped 인데도 success 다(#97에서 이것이 full 실패를 가렸다). 목록의 한 줄이 아니라 **단계 결론**을 본다. 국토부 응답은 날짜별로 다시 받을 수 없다(#62).

## 데이터 진척 경고의 출구 (#657)

`Schedule watchdog` 의 `report` job 이 `watch` 의 판정을 받아 이슈를 연다. 권한은 그 job 의 `issues: write` 와 체크아웃용 `contents: read` 뿐이고, `watch` 는 읽기 둘 그대로다. 규칙은 `scripts/report-data-progress.ts` 머리 주석, 코드 목록은 `scripts/check-data-progress.ts` 의 `ISSUE_GROUPS`·`NO_ISSUE_GROUPS` 다.

- **제목·라벨:** `[오류] 데이터 진척 경고: <묶음>`, `audit`·`bug`. 묶음은 소스 이름의 첫 조각이고 `series/*` 15개가 1건이다. 같은 제목이 열려 있으면 아무것도 안 한다.
- **시점:** 묶음에 경고가 있으면 그 틱에 연다. 상태 파일이 없어 연속을 세지 않는다. 슬롯 누락·중간 빈 달·`progress.json` 없음은 한 틱의 경고로 열린다.
- **상한:** 틱당 새 이슈 3건. 넘친 묶음은 `::warning::` 을 남기고 다음 틱에 열린다.
- **이슈 없는 것:** `news`·`ledger`·빌더 산출물(F2). 실패 단계에서 빨간 run 과 메일이 된다. 묶음에 실패 판정만 있어도 열지 않는다. `official-price` 는 #660 실패 메일과 겹칠 수 있다.
- **닫기:** 자동으로 닫지 않고 댓글도 없다. 사람이 닫고, 경고가 남아 있으면 다음 틱에 다시 열린다.
- **받는 주인: ops.** 봇이 연 이슈는 작성자가 소유자가 아니라 일일 운영 사이클이 집어 가지 않을 수 있다(`authorAssociation` 실측은 #657 PR). 그래서 ops 는 `audit` 라벨 열린 이슈를 직접 본다: `gh issue list -R kyhsa93/jipgye -l audit --state open`. 사이클 쪽 처리는 cto 가 정한다.
- **`report` 가 빨간 때:** `watch` 의 결과가 비었거나 못 읽음, 코드 목록에 없는 소스, 열린 이슈 목록을 못 읽음, 이슈를 못 만듦. 어느 쪽이든 그 틱의 경고가 이슈로 안 올라간 것이니 로그의 `::error::` 를 본다. 권한 오류(403)가 저장소 설정 때문이면 계정 콘솔 건으로 소유자에게 올린다.
- **시험 표지:** `gh workflow run schedule-watchdog.yml -f issue_test=dispatch-test` 는 판정과 무관하게 `...: dispatch-test` 이슈 1건을 연다(둘째 실행은 0건). 쓰기 경로 점검용이고, 실측 뒤 닫는다.

## 하지 않는 것

- force-push·이력 다시 쓰기 금지. 되돌림은 `git revert` 새 커밋 1건(PR, cto 병합)이고 main 에 직접 푸시하지 않는다.
- 소유자 허락 없이 수동 실행·재실행하지 않는다. 소유자가 `! gh workflow run daily-update.yml -f mode=full` 처럼 직접 돌리고, 에이전트는 요청만 한다. Daily·Summarize 는 한 줄(`digest-pipeline`)이라 진행 중이면 겹쳐 돌리지 않는다. `Deploy site` dispatch 는 롤백 전용이다.
- `docs/data`·`raw` 를 손으로 고쳐 숫자를 맞추지 않는다(수집기·빌더를 고친다). `raw` 커밋은 되돌리지 않는다. 시크릿(`MOLIT_*`·`ECOS_API_KEY`)을 이슈·댓글·로그·커밋에 쓰지 않는다. 시험을 끄거나 COUNT 를 내려 초록을 만들지 않는다. 유료 API·새 로컬 cron·서버는 쓰지 않는다.

## 소유자 결정 트리거

- **돈:** 키 재발급·유료 전환. **신원:** 계정·로그인·저장소 설정·시크릿 값, 수동 실행 허락. **법:** 개인정보·이용허락에 걸림.
- 공개 숫자가 틀린 채 노출된 정황, 첫 실패부터 복구까지 24h 초과, `source-age` ≥3일, 같은 원인이 7일 안에 두 번째. 올리지 않는다: 늦은 틱, 다음 틱에 자연 복구된 일시 장애(이슈 댓글 한 줄).
- 일정 재검토(#294): 23:07 틱 누락이 30일 안 2회 이상, 또는 23:07 칸 지연 최대가 6h 초과(54h 창 위험)이면 보조 cron 을 R2 PR 로 판단한다.
