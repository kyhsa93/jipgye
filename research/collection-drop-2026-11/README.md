# 일 수집 건수 감소와 보류 규칙 (#863)

원본 슬롯 이력(`raw/sale`, `raw/rent`의 git 이력)에서 슬롯별 건수 감소 사건을 세고, 보류 규칙을 그 이력에 다시 돌려 본다. 호출 0회, git 읽기만 한다.
규칙과 값은 #863 data-analyst 판정(2026-11-15)이 정했다. 구현은 `scripts/realestate-guard.ts`이다.

## 재현

저장소 루트에서 Python 3로 돌린다. `drops.py`의 두 번째 인자는 읽을 기준이다(판정은 `40a5d5d2`, 생략하면 `HEAD`). 57커밋을 읽는 데 1분쯤 걸린다.

```sh
cd research/collection-drop-2026-11
python3 drops.py /tmp/drops.pkl 40a5d5d2     # 이력 읽기: 57 commits 1250 slots 5050 versions
python3 events.py /tmp/drops.pkl /tmp/events.pkl   # 감소 사건표: 17 drop events
python3 sim.py /tmp/drops.pkl                # 보류 재생(N·H를 바꿔 돌림)
python3 freshness.py /tmp/drops.pkl          # 보류가 수집 신선도(source-age)를 바꾸는가
```

| 파일 | 하는 일 |
|---|---|
| `drops.py` | 원본 커밋을 차례로 이어 바뀐 슬롯 파일의 판을 읽는다. 행 신원은 `rgstDate`·`cdealType`·`cdealDay`·`aptDong`을 뺀 나머지 칸이다 |
| `events.py` | 직전 저장보다 `count`가 준 판을 모두 적는다. 빠진 행이 돌아왔는지, 같은 해시로 돌아왔는지도 적는다 |
| `sim.py` | 각 원본 커밋을 한 수집 회차로 보고 보류 규칙(저장 20행 이상, 응답×2 < 저장 또는 저장−응답 ≥ N, H 수집일)을 다시 돌린다 |
| `freshness.py` | N=10·H=3 보류에서 가장 최근 달 슬롯의 최신 `observedAt`이 실제 이력과 달라지는 회차를 센다 |

## 결과(기준 `40a5d5d2`)

- 감소 사건 17건: 1행 14건, 125행(전월세 11260-202610, 10-15), 165행(매매 11710-202609, 10-15), 313행(매매 11230-202610, 11-01).
- `sim.py` N=10·H=3: 걸린 사건 3, 보류한 회차 7, 3일 뒤 반영 1, 늦어진 새 행 48행(행×일 90, 최대 3일). N을 2~50 어디에 두어도 같다.
- 늦어진 48행은 같은 기간 새로 보인 신원 60,924개(슬롯마다 연속한 두 판 사이에 새로 생긴 신원의 합: 매매 12,070·전월세 48,854)의 0.08%다.
- `freshness.py`: 같은 날 보류한 슬롯은 최대 2개(10-15·10-16)다. 보류가 종류별 최신 `observedAt`을 바꾼 회차는 0회다. 다음 회차 직전 경과일이 2일 이상인 회차는 실제 이력과 보류 재생 모두 20회이고 같은 회차다. 이력 구멍(09-03~09-30, 10-02·03·11·23은 커밋이 없다)과, 가장 최근 달 슬롯이 그날 하나도 바뀌지 않은 회차(10-05·10-06 매매, 11-02 매매 등) 때문이며 보류와 무관하다.
- 한계: 보류한 슬롯이 그 종류의 가장 최근 달에서 이틀 넘게 유일하게 바뀌는 슬롯이면 `source-age`가 2일 경과(낡음)로 본다. 이 이력에서는 0회다 - 보류한 슬롯이 가장 최근 달에 있던 회차는 전월세 11260-202610(10-15~17) 셋뿐이고, 그날 같은 달 다른 전월세 슬롯도 바뀌었다.

## 행 신원을 어떻게 셌나

정의 원본은 `scripts/realestate-first-seen.ts`의 `IDENTITY_SKIP`이다. `drops.py`의 `VOLATILE`은 그 사본이고, `test/realestate-guard.test.mjs`가 두 목록이 같은지 대조한다.

`drops.py`는 네 칸(`rgstDate`·`cdealType`·`cdealDay`·`aptDong`)을 빼고 행 신원을 센다. 이 네 칸만 바뀐 행은 같은 거래로 본다.
세 칸만 빼면(`aptDong` 포함) 등기일과 동이 함께 붙어 돌아온 행이 「돌아오지 않은」 것으로 보인다. 그러면 큰 사건의 복귀가 재현되지 않고, 늦어진 행은 50행(행×일 92)이 된다.

「늦어진 새 행」은 신원 기준이다. `itemKey`(행 전체 해시) 기준으로 세면 11230-202610에서 1행이 0이 아니다. 10-31에 있던 거래 하나가 11-02에 등기일·동이 붙어 해시가 바뀌었는데,
실제 이력은 그 행을 11-02로, 보류 재생은 11-03으로 찍는다. 새 거래가 아니라 재도장이 하루 밀린 것이다(`test/realestate-guard.test.mjs` 재생 ③).
