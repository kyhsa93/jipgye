같은 갈아타기 화면의 가격대·연식·면적대 구간(`scripts/segment-change.ts`)과 해제 화면의 직거래 격차(`scripts/direct-deals.ts`)는

## 2. 사전 고정 (pm, #909 본문 v3 「사전 고정」 절 그대로 — 결과를 본 뒤 바꾸지 않는다)

data-analyst는 이 절을 PREREG.md에 그대로 옮긴다. 후보 R = 400 / 1,000 / 2,000 / 4,000번이다. 씨앗은 20개(20261001 + 7919·k, k = 0~19)다. 기준은 100,000번, 씨앗 20261001이다. 모두 #858과 같다.

### S1. segment — 주지표와 문턱: 비율 문턱(cpo 보완 2의 (나))
- 주지표 F_pair(R, s)는 그 입력의 공개 쌍 P개 가운데 판정(true/false)이 기준과 다른 쌍 수다. 쌍은 같은 차원 안에서만 센다(가격대 끼리, 연식 끼리). 입력 A에서 P = 13(가격대 10 + 연식 3)이다. 면적대는 쌍이 없다(빌더가 `pairs.area`를 만들지 않는다).
- **문턱은 #858 문턱의 비율이다.** #858은 276쌍에서 중앙값 ≤ 1, 최댓값 ≤ 3을 허용했다. 이는 쌍 비율로 0.36%·1.09%다. P쌍에서 허용하는 수는 중앙값 ≤ ⌊P × 1/276⌋, 최댓값 ≤ ⌊P × 3/276⌋다. **P = 13이면 둘 다 0이다. 곧 20개 씨앗 모두 13쌍 판정이 기준과 같아야 통과다.**
- 이유
  - 276쌍의 절대 개수(최댓값 3)를 13쌍에 그대로 쓰면 23%가 뒤집혀도 통과다. 문턱이 결과를 미리 정해 버린다.
  - 이 화면이 방문자에게 하는 말은 「구별된다」 문장이다. 씨앗을 바꿨다고 그 문장이 바뀌면 안 된다. #858이 허용한 흔들림을 쌍당 비율로 그대로 옮기는 것이 같은 기준이다.
  - 엄격해서 어느 후보도 못 넘을 수 있다. 그때는 아래 S4의 「통과 후보 없음」 처리를 따르고, 남는 뒤집힘을 method에 숫자로 적는다. 400번에서 경계에 붙은 쌍이 없으면 400번이 통과하고 바꾸지 않는다. 그래서 결과는 데이터가 정한다.
- 차원별 값(가격대 /10·연식 /3)을 표에 함께 적는다. 판정은 합 P로 한다.
- 보조 지표(기록만, 판정에 쓰지 않음): 12구간(면적대 포함) 끝값 low·high(빌더의 `pct` 반올림, 0.1%p)가 기준과 다른 씨앗 수.
  - 판정에 쓰지 않는 이유가 있다. segment 화면의 주장은 쌍 판정이다. 24개 끝값을 0.1%p에서 묶으면 반올림 경계 하나로 모든 후보가 떨어질 수 있다. 그러면 화면의 주장과 무관한 이유로 R이 정해진다.

### S2. direct — 지표 단위와 문턱
- 판정 단위는 **공개되는 구간 하나하나**다. 지금은 서울 하나다. 측정 시점(입력 A·B 각각)에 칸이 20칸 이상인 자치구가 생기면 그 구도 같은 문턱을 따로 적용하고, 모든 구간이 채워야 통과다.
  - 직거래 화면과 월간 보고 표에 실제로 찍히는 숫자가 그 구간들이라서 이렇게 정한다.
- 지표 D(R, 구간)는 20개 씨앗 가운데 그 구간의 low 또는 high가 표시 정밀도(빌더의 `round1`, 0.1)에서 기준과 다른 씨앗 수다.
- **문턱: D ≤ 2(20개 중 10% 이하).**
  - 이유: 이 화면은 쌍 판정을 하지 않는다. 바뀌는 것은 「구별된다」 같은 주장이 아니라 숫자의 끝자리다. 그래서 segment(0)보다 너그럽게 둔다.
  - 그래도 「얼려 두고 채점·정정한 기록」에서 날마다 공개 숫자를 견줄 때 씨앗 탓의 0.1 변화가 데이터 변화로 읽히지 않아야 한다. 그래서 「열 번 다시 재면 아홉 번은 같은 숫자」를 하한으로 둔다.
- 기준값 자체가 반올림 경계(…x5)에 붙어 있으면 어느 R도 못 넘을 수 있다. 그때도 S4의 「통과 후보 없음」 처리를 따른다.

### S3. 빌드 시간 예산
- **두 빌더의 증가분을 합쳐 ≤ 7.7초(이 머신)로 한다.** #858 PREREG 예산 30초에서 PR #912가 쓴 22.3초를 뺀 값이다. #908이 같은 7.7초를 상한으로 썼다(#908 pm 판정).
- 잴 때는 원본 코드를 쓴다. segment는 `districtRows(…, { rounds })`, direct는 `band(gaps, { rounds })`다. R마다 3회 재서 중앙값을 내고, 1분 부하 평균을 찍는다.
- CI 환산도 표에 적는다(11-16 Daily segment 1.18초 × #858 러너 배율 1.36~1.91). 기록일 뿐 관문은 아니다.
- 나누는 순서: **direct를 먼저 고른다**(cto 예상으로 4,000번이어도 +0.1초 안팎). segment는 7.7초에서 direct가 고른 R의 증가분을 뺀 나머지 안에서 고른다.
- cto 예상(측정이 아니다): segment 4,000번 +9.7초는 예산 밖이고, 2,000번 +4.6초는 예산 안이다.

### S4. 선택 규칙 (빌더마다 따로, #858과 같다)
- 예산 안 후보 가운데 문턱(S1·S2)을 **모든 판정 입력에서** 채우는 가장 작은 R을 고른다. 판정 입력은 A와 B다. B=A면 A 하나다.
- 그런 R이 없으면 **예산 안의 가장 큰 R**을 고른다. 그 R에서 남는 값을 method ko·en에 숫자로 적는다. segment는 F_pair의 범위·중앙값 / P, direct는 구간마다 D / 20이다.
- 고른 R이 400이면 「바꾸지 않음」, 아니면 「바꿈」이다. 두 빌더의 결론은 다를 수 있다.
- 문턱·예산·선택 순서·단위는 결과를 본 뒤 바꾸지 않는다.

### S5. 입력
- A = 2026-11-16 Daily run 43793620193(원본 `f692748e`, 데이터 `cd20a99b`).
- B = PREREG 커밋 뒤 첫 정기 Daily다. 측정 전에 그 원본·데이터 sha를 이 이슈에 댓글로 먼저 단다.

## 3. 옮겨 적으며 정한 것 (data-analyst, 측정 전 — 사전 등록 검토에서 cto·cpo·pm 이 본다)

2절은 고치지 않는다. 아래는 2절을 스크립트로 옮기며 문장만으로는 하나로 정해지지 않던 곳이다. 검토에서 수정 요청이 오면 측정
전에 고치고, 그 수정 커밋이 등록 sha 가 된다(7절 9).

### 3.1 기준 씨앗: 1 (본문 첫 문단의 「씨앗 20261001」과 다르다 — pm 확인 요청)
- 2절 첫 문단은 「기준은 100,000번, 씨앗 20261001이다. 모두 #858과 같다」이다. 그런데 #858 PREREG
  (`research/district-change-rounds-2026-11/PREREG.md` 「기준」)과 cto 착수 조건 4는 **씨앗 1** 이다. 두 문장이 서로 맞지 않는다.
- 씨앗 1로 한다. 이유
  - 본문 문장이 스스로 「#858과 같다」고 한다. #858 기준은 씨앗 1이고 「후보 씨앗과 겹치지 않음」을 이유로 적었다.
  - `band` 는 씨앗에서 시작하는 한 줄의 난수열을 회차 순서대로 쓴다. 씨앗 20261001로 100,000번을 돌리면 처음 400회의 중앙값이
    후보 (400번, k = 0)과 같은 400개다. 기준이 후보 하나와 같은 추첨을 나눠 갖게 되어, 그 후보가 기준에 가깝게 나온다.
- 이 결정은 측정 전에 정한다. pm 이 20261001이 맞다고 하면 `lib-909.mjs` 의 `BASE.seed` 한 줄을 바꾸고 그 커밋이 등록 sha 가 된다.

### 3.2 P 는 입력마다 기준 실행에서 센다
- P = 기준 실행에서 칸이 `MIN_CELLS`(30) 이상인 가격대 구간끼리의 쌍 수 + 연식 구간끼리의 쌍 수. 칸 수는 재추출 횟수와 무관하므로
  모든 R·씨앗에서 같다. analyze 가 이 P 를 공개 파일의 `pairs.price`·`pairs.age` 키 수와 대조하고, 다르면 멈춘다.
- 허용 수는 2절 S1 그대로 ⌊P·1/276⌋·⌊P·3/276⌋ 이다. P ≤ 91 이면 둘 다 0, P = 92~183 이면 중앙 0·최대 1 이다. 입력 A 의 P = 13
  (공개 파일 cd20a99b, 가격대 10 + 연식 3)이라 중앙 0·최대 0 이다.
- 20개 씨앗의 중앙값은 정렬해 10·11번째의 평균이다(#908 과 같다).

### 3.3 직거래 판정 구간은 입력마다 공개 파일과 같은 규칙으로 정한다
- 서울(모든 자치구 칸을 모은 것, `directDealStats` 의 `allGaps`) + 그 입력에서 칸이 `MIN_CELLS`(floor-gap.ts, 20) 이상인
  자치구. `summarizeGaps` 가 값을 내는 조건(`gaps.length < minCells` 면 비움)과 같다.
- 입력 A 는 서울 하나다(칸 112, −16.9~−11.8, 칸이 가장 많은 자치구 12칸 — cd20a99b 공개 파일). 판정 구간이 늘면 구간마다
  D ≤ 2 를 따로 채워야 통과다(2절 S2).

### 3.4 S5 의 「B=A」는 공개 파일까지 같을 때만 (pm 확인 요청)
- 2절 S5 는 `raw/sale` 0파일이면 B=A 로 판정 입력을 A 하나로 한다.
- 그런데 두 빌더의 칸 키는 `readSameNames()` 를 쓴다(segment: build-district-change.ts 141행, direct: build-cancellation.ts
  138행). 이 함수는 `raw/sale` 과 `raw/rent` 를 모두 읽는다(realestate-raw.ts `KINDS = ["sale", "rent"]`). 전월세 원본은 날마다
  바뀐다(8eb314f7 → cd20a99b 9파일, 5절). 그래서 `raw/sale` 이 그대로여도 동명 판정이 바뀌면 칸이 달라질 수 있다.
- 그래서 B=A 는 둘 다일 때만 한다.
  - `git diff --stat f692748e <B 원본> -- raw/sale` 0파일
  - A·B 의 공개 `segment-change.json`·`direct-deals.json` 이 `updatedAt` 말고 같다
- `raw/sale` 은 0파일인데 공개 파일이 다르면 판정 입력을 A·B 둘로 한다. 이 경우 S5 의 「1파일 이상」과 같이 둘 다에서 문턱을 채워야 한다.
- 공개 파일 비교는 400번·지금 씨앗으로 이미 공개된 값이라 측정 결과가 아니다. 결과를 보기 전에 정해진다.
- pm 이 「raw/sale 만 본다」로 정하면 `measure-909.sh` 의 판정 입력 분기 한 줄을 바꾸고 그 커밋이 등록 sha 가 된다.

### 3.5 시간
- 증가분은 같은 실행 안의 400번 대비다: 증가(R) = 중앙값(R) − 중앙값(400). 400번은 0이다.
- 회차마다 후보 넷을 돌아가며 잰다(한 후보를 몰아 재면 그사이 부하 변화가 한 후보에만 실린다).
- segment 는 `districtRows(byKey, defs, { rounds })` 세 차원(가격대·연식·면적대) + `pairVerdicts`(가격대·연식)이다. 빌더의
  `segmentRows` 가 부르는 것과 같다. direct 는 판정 구간마다 `band(gaps, { rounds })` 다.
- 시작 때 1분 부하 평균이 코어 수의 절반을 넘으면 60초씩 최대 10번 기다린다. 그래도 넘으면 그대로 재고 그 사실을 찍는다.
  #917 브라우저 측정과 같은 머신을 쓰기 때문이다. 기다린 횟수와 시작·끝 부하는 결과에 같이 싣는다.
- 입력 A 로 잰다(B 가 있어도 칸 수가 거의 같다). CI 환산은 두 가지를 기록만 한다.
  - segment 증가 × 1.36~1.91
  - 11-16 Daily segment 1.18초 × (이 머신 R / 이 머신 400)

| F_pair 가격대·연식 | 위를 차원별로(/P_가격대, /P_연식) | 기록 |
| 뒤집힌 쌍 | 한 번이라도 뒤집힌 쌍과 횟수 /20 | 기록 |
| 보조 끝값 | 12구간(면적대 포함, 칸 ≥ 30) 가운데 low·high(`pct`)가 기준과 다른 씨앗 수, 구간별·「하나라도」 | 기록(2절 S1 보조) |
| D(R, 구간) | 직거래 판정 구간마다 low 또는 high(`round1`)가 기준과 다른 씨앗 수 | S2: 구간마다 ≤ 2 |
| 시간 증가 | 3.5절 | S3: direct 증가 + segment 증가 ≤ 7.7초, direct 먼저 |

선택(S4)도 analyze 가 낸다. 빌더마다 따로 한다.
1. direct: 예산 7.7초 안 후보 가운데 모든 판정 입력에서 S2 를 채우는 가장 작은 R. 없으면 예산 안 가장 큰 R.
2. segment: 예산 7.7 − direct 가 고른 R 의 증가 안에서 같은 규칙으로 S1.
3. 「통과 후보 없음」이면 남는 값을 같이 찍는다. segment 는 「{범위}쌍(중간값 {m}쌍) / P」, direct 는 구간마다 「D/20」이다. 이것이
   본문 「method 문장」의 `{범위}`·`{m}`·`{k}` 자리에 들어간다. 판정 입력이 둘이면 입력마다 따로 적는다.

## 7. 무효·멈춤

무효면 결과를 싣지 않고 다시 등록한다. 멈추면 판정하지 않고 원인을 #909 에 적는다. `measure-909.sh` 가 1~7 을 측정 전에 확인한다(4 는 prep·verify).

1. **등록 무효(cto 조건 11).** 측정을 시작할 때 `git diff --quiet <등록 sha> origin/main -- <목록>` 이 종료 0 이 아니면 무효다
   (스크립트 종료 4). 목록: `scripts/district-change.ts`, `scripts/segment-change.ts`, `scripts/direct-deals.ts`,
   `scripts/build-direct-deals.ts`, `scripts/build-cancellation.ts`, `scripts/build-district-change.ts`, `scripts/floor-gap.ts`,
   `scripts/complex-price.ts`, `scripts/cancel-by-price.ts`, `scripts/realestate-raw.ts`. 특히 #900 후속이 두 빌더의 읽기 경로를
   덧씌움으로 바꾸면 무효다. 측정 전에 `git fetch` 로 origin/main 을 새로 받는다.
2. **작업 트리.** 측정 작업 트리의 HEAD 가 등록 sha 가 아니거나, scripts·이 폴더가 그와 다르면 멈춘다. raw·docs/data 는
   `git restore --source=<데이터 커밋> --staged --worktree -- raw docs/data`(no-overlay, 없는 파일은 지운다)로 꺼내고
   `git diff --cached --quiet <데이터 커밋> -- raw`·`-- docs/data` 가 종료 0 이 아니면 멈춘다. `git checkout <커밋> -- raw` 는
   쓰지 않는다(cto 조건 7).
3. **입력 B.** 아래 가운데 하나라도 아니면 멈춘다.
   - B 원본이 등록 sha 의 후손이다.
   - B 원본이 B 데이터의 조상이다.
   - B 데이터가 origin/main 에 있다.
   - 등록 sha 와 B 사이에 다른 Daily 데이터 커밋(「데일리 데이터 갱신」)이 0개다.
   그 사이에 수동 실행이 끼었으면 그 사실과 run 번호를 #909 에 적고 pm·cto 판단을 받는다. 결과를 보기 전이다.
4. **재현 실패.** prep·verify 가 실패하면 그 입력은 측정하지 않는다.
   - 원인이 측정 스크립트면 고친 커밋을 새 등록 sha 로 삼는다. 입력 B 는 그 새 등록 뒤 첫 정기 Daily 로 다시 정한다.
   - 원인이 입력(등록 sha 와 B 사이에 무효 목록 밖 파일이 바뀌어 B 공개 파일을 등록 코드로 못 만드는 경우 포함)이면 pm·cto 에 올린다.
5. **node_modules = lockfile(cto 조건 8).** node_modules 의 실제 폴더(링크 대상, 보통 `~/workspace/jipgye`)에서 `npm ls --all` 이
   종료 0 이어야 한다. 그 폴더와 측정 작업 트리의 `package-lock.json` 이 `cmp` 로 같아야 한다. 링크를 건 작업 트리 안에서
   `npm ls` 를 돌리지 않는다. 손 단계가 아니라 `measure-909.sh` 의 멈춤 검사다.
6. **키 환경변수(cto 조건 9).** 모든 node 실행은 `env -i PATH HOME` 으로 한다. MOLIT_API_KEY·MOLIT_RENT_API_KEY·BUILDINGHUB_API_KEY·
   GITHUB_TOKEN 이나 이름이 `*_KEY`·`*_TOKEN`·`*_SECRET` 인 변수가 있으면 종료 3, 전부 무효다.
7. **네트워크(cto 조건 9).** 모든 측정 프로세스는 fetch·http(s).request/get·net.connect/createConnection·tls.connect·dns.lookup 을
   막고 시도 수를 센다. prep·verify·time·analyze 는 끝 줄에, 재추출 81×입력 수 개는 결과 파일에 수를 남기고 analyze 가 합을
   마지막 줄 바로 위에 찍는다. 0 이 아니면 종료 2, 전부 무효다.
8. **git.** git 명령은 모두 `timeout -k 10 600` 으로 감싼다. git 이 D 상태로 멈추면 다시 시도하지 않고, PID·명령을 cto 에 넘긴다.
9. **사전 등록 검토 수정.** cto·cpo·pm 검토에서 수정 요청이 오면 측정 전에 고친다. 그 수정이 main 에 올라간 커밋이 등록 sha 다.
   B 는 그 등록 뒤 첫 정기 Daily 다.
10. **실행 환경 오류 재실행(cto 조건 10, #900 cto 권고).** 의존성·권한·디스크 같은 실행 환경 오류로 중단되면, 새 등록 sha 없이
    처음부터(`measure-909.sh` 를 같은 인자로) 다시 돈다. 세 조건을 모두 채워야 한다.
    - (a) 8절 「결과를 본 뒤 바꾸지 않는다」 항목이 바뀌지 않았다.
    - (b) 중단 전에 찍힌 줄이 재실행 출력의 같은 줄과 같다. 다만 기계 상태 줄은 뺀다: `시각`·`부하`·`디스크 오류 줄`, 재추출
      시작·끝 시각, `[time …]` 줄. `[time …]` 줄이 1차에 찍혔다면 두 회의 시간 줄을 모두 결과 댓글에 싣는다. 두 시간으로 S4 의
      고른 R 이 달라지면 data-analyst 가 고르지 않고 cto·pm 에 올린다.
    - (c) 1차 출력의 sha256 을 결과 댓글에 싣는다.
    스크립트나 입력이 원인이면 이 규칙에 해당하지 않는다. 4 대로 새 등록으로 간다.
11. **순서 확인(cto 조건 12).** 결과 커밋 전에 결과를 올릴 가지(main 후손)에서
    `node scripts/check-prereg-order.ts --prereg <등록 sha 40자> --prereg-path research/segment-direct-rounds-2026-11/PREREG.md --output research/segment-direct-rounds-2026-11/measure-909.out`
    이 통과해야 한다. 통과 출력을 판정 댓글에 싣는다. 측정 작업 트리(HEAD = 등록 sha)에서 돌려도 되지만 결과 커밋은 그 뒤 가지에 둔다.

## 9. 실행 순서

git fetch -q
REG=<등록 sha 40자>; BDATA=<B 데이터 커밋 40자>; BRAW=<B 원본 커밋 40자>
